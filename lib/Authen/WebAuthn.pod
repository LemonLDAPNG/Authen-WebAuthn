# PODNAME: Authen::WebAuthn
# ABSTRACT: A library to add Web Authentication support to server applications

=head1 SYNOPSIS

This module lets you validate L<Web Authentication|https://www.w3.org/TR/webauthn/> registration and authentication responses.

It can also build the options for those requests.

The transmission of requests and responses from the application server to the
user's browser, and interaction with the WebAuthn browser API is also out of
scope and could be handled by a dedicated JS library.

To register a new device:

    # Obtain registration response from web browser
    # Then,
    my $webauthn_rp = Authen::WebAuthn->new(
        rp_id  => "app.example.com",
        origin => "https://app.example.com"
    );

    my $registration_result = eval {
        $webauthn_rp->validate_registration(
            challenge_b64          => ... ,
            requested_uv           => ... ,
            client_data_json_b64   => ... ,
            attestation_object_b64 => ... ,
        )
    };
    if ($@) {
        die "Error validating registration: $@";
    }

To authenticate a user:

    # Obtain authentication response from web browser
    # Then,
    my $webauthn_rp = Authen::WebAuthn->new(
        rp_id  => "app.example.com",
        origin => "https://app.example.com"
    );

    my $validation_result = eval {
        $webauthn_rp->validate_assertion(
            challenge_b64          => ...,
            credential_pubkey_b64  => ...,
            stored_sign_count      => ...,
            requested_uv           => ...,
            client_data_json_b64   => ...,
            authenticator_data_b64 => ...,
            signature_b64          => ...,
            extension_results      => ...,
        )
    };
    if ($@) {
        die "Error validating authentication: $@";
    }

=attr rp_id

The identifier of your Relying Party. Usually, this is set to the domain
name over which your application is accessed (app.example.com).

=attr origin

The origin, as defined by the HTML standard, that your Relying Party is
expecting to find in registration or authentication responses. This must
contain the scheme and port of your application, but no path
(http://app.example.com:8080 or https://app.example.com)

It can also be an arrayref of origins, all of which are accepted. An Android
application, for instance, reports an origin derived from the key that signed
it (C<android:apk-key-hash:...>), and a development build is not signed with
the same key as the release.


=attr allow_cross_origin

WebAuthn can be used from an iframe whose origin differs from the top-level
page's, if the page allows it. By default such requests are refused
(C<crossOrigin> is true in the client data).

Set this to 1 to accept them, or to an arrayref of the top-level origins you
accept, which are compared with C<topOrigin> in the client data. Any other
value, such as a single origin as a string, makes such requests fail.

A C<topOrigin> in the client data is checked the same way even when
C<crossOrigin> is not set.

=method generate_registration_options

    my $options = $webauthn_rp->generate_registration_options(
        rp_name   => "Example",
        user_id   => $user_id,
        user_name => 'alice@example.com',
    );

Builds the C<PublicKeyCredentialCreationOptions> for a registration, as a
hashref that can be serialized to JSON and given to
C<PublicKeyCredential.parseCreationOptionsFromJSON()> in the browser. Binary
values are base64url-encoded.

Store C<< $options->{challenge} >> on the server, with the session for
instance, and pass it to C<validate_registration> as C<challenge_b64>.

It takes the following named arguments

=over 4

=item rp_name

The name of your Relying Party, as shown to the user. Required.

=item user_id

The user handle: an opaque identifier of the user account, at most 64 bytes
(longer is refused), which must not contain personal information. Required.

=item user_name

The name of the user account, such as a login or an email address. Required.

=item user_display_name

A friendlier name for the user account. Defaults to C<user_name>.

=item challenge_b64

The base64url-encoded challenge. By default, 32 random bytes are generated.

=item allowed_algs

An arrayref of COSE algorithm identifiers, in order of preference. Defaults to
C<[-8, -7, -257]> (EdDSA, ES256 and RS256), which WebAuthn recommends for
supporting a wide range of authenticators. Pass the same value to
C<validate_registration>.

WebAuthn advises against offering the fully-specified identifiers -9, -51, -52
and -19 here, as many authenticators do not know them; offer ES256, ES384,
ES512 and EdDSA instead.

=item requested_uv

C<required>, C<preferred> (the default) or C<discouraged>. Pass the same value
to C<validate_registration>.

=item attestation

The attestation conveyance preference: C<none> (the default), C<indirect>,
C<direct> or C<enterprise>.

=item exclude_credentials

An arrayref of the credentials the user already has, so that the same
authenticator is not registered twice. Each item is a base64url-encoded
credential ID, or a hashref with an C<id> and an optional arrayref of
C<transports>.

=item resident_key

C<required>, C<preferred> or C<discouraged>. Omitted by default. C<required>
also sets C<requireResidentKey>, for browsers that predate C<residentKey>.

=item authenticator_attachment

C<platform> or C<cross-platform>. Omitted by default.

=item timeout

How long the browser may wait for the user, in milliseconds. Omitted by
default.

=item hints

An arrayref of C<security-key>, C<client-device> and C<hybrid>, in order of
preference, to guide the browser's choice of authenticator. Omitted by
default.

=item extensions

A hashref of client extension inputs, such as C<< { credProps => JSON::true } >>,
passed to the browser as given. Omitted by default.

=back

Values outside the ones listed above for C<requested_uv>, C<attestation>,
C<resident_key>, C<authenticator_attachment> and C<hints>, and a C<timeout>
that is not a positive whole number, make this method croak.

=method generate_assertion_options

    my $options = $webauthn_rp->generate_assertion_options(
        allow_credentials => \@credential_ids,
    );

Builds the C<PublicKeyCredentialRequestOptions> for an authentication, as a
hashref that can be serialized to JSON and given to
C<PublicKeyCredential.parseRequestOptionsFromJSON()> in the browser.

Store C<< $options->{challenge} >> on the server and pass it to
C<validate_assertion> as C<challenge_b64>.

It takes the following named arguments, all optional

=over 4

=item challenge_b64

The base64url-encoded challenge. By default, 32 random bytes are generated.

=item requested_uv

C<required>, C<preferred> (the default) or C<discouraged>. Pass the same value
to C<validate_assertion>.

=item allow_credentials

An arrayref of the credentials that may be used, in the same format as
C<exclude_credentials> above. Leave it out to let the user pick a discoverable
credential.

=item timeout

How long the browser may wait for the user, in milliseconds. Omitted by
default.

=item hints, extensions

As for C<generate_registration_options>.

=back

C<requested_uv>, C<hints> and C<timeout> are checked as for
C<generate_registration_options>.

=method validate_registration

This method validates the registration response emitted by the authenticator.

It takes the following named arguments

=over 4

=item challenge_b64

The base64url-encoded challenge that was submitted to the authenticator

=item requested_uv

Whether or not the Relying Party required user verification for this operation.
Possible values are C<required>, C<preferred> (the default) and
C<discouraged>; any other value makes validation fail.

=item client_data_json_b64

The base64url-encoded client data received from the authenticator

=item attestation_object_b64

The base64url-encoded attestation object received from the authenticator

=item trust_anchors

If the authenticator response contains an attestation, C<validate_registration> will
attempt to chain it to a trusted root certificate.
You need to explicitly specify which certificates to trust if your authenticator provides an attestation.

If you requested "none" as an attestation format while initiating the registration flow, there is no need to provide any trust anchors.

This optional parameter can either be an arrayref of strings representing PEM-encoded certificates, or a subref which returns a arrayref of PEM-encoded certificates:

    sub {
        my (%params) = @_;
        my $aaguid = $params{'aaguid'};
        my $attestation_type = $params{'attestation_type'};
        my $attestation_format = $params{'attestation_format'};
        ...
        return [ $pem1, $pem2, ...];
    }

=item allowed_attestation_types

If you want to restrict the allowed attestation types, you can pass an arrayref of strings as the C<allowed_attestation_types> parameter.

Currently supported values are C<None>, C<Self>, C<Basic>, C<AttCA> (the
C<tpm> format) and C<AnonCA> (the C<apple> format)

By default, all attestation types are allowed

=item allow_untrusted_attestation

By default, if an attestation type such as C<Basic> is used by the
authenticator and a correct trust_anchor could not be found, the validation
will fail as mandated by the WebAuthn specification. However, in some cases it
is permitted to allow the registration to proceed, but treat it as C<Self>
attestation.

This setting allows you to successfully validate registration, but change the
type to C<Self> if a trusted certificate was not provided in the
C<trust_anchors> parameter.

=item allowed_algs

An arrayref of the COSE algorithm identifiers you offered the authenticator in
C<pubKeyCredParams>, such as C<[-7, -257]> for ES256 and RS256. Registration
fails if the credential public key uses any other algorithm.

By default, every algorithm supported by this module is accepted, including
RS1, which signs with SHA-1.

=item allow_unknown_attestation_format

By default, if an unimplemented attestation format is encountered, registration
validation will fail.

This setting allows you to successfully validate registration, but change the
attestation type to C<None> if an unimplemented attestation format is
encountered.

=item android_key_require_tee

The C<android-key> format describes the key in two authorization lists: what
the device's trusted execution environment enforces, and what Android's
software enforces. By default, the checks the specification asks for (the key
was generated by the authenticator, is for signing, and is scoped to the RP
ID) are satisfied by either list. Set this to accept only the trusted
execution environment's.

=item extension_results

The client extension outputs: what C<getClientExtensionResults()> returned in
the browser, as C<PublicKeyCredential.toJSON()> writes them (bytes in
base64url). The outputs of the extensions this module knows (C<appid>,
C<appidExclude>, C<credProps>, C<largeBlob>, C<prf>) are checked for type;
others are passed through. An output of the wrong type is refused if it was
requested, and left out of the results if C<requested_extensions> is not
given.

=item requested_extensions

The C<extensions> you passed to the browser. Given, an output for an extension
you did not request is ignored, or refused with
C<< allow_unsolicited_extensions => 0 >>. The same applies to the authenticator
extension outputs in the authenticator data (C<credProtect>, C<hmac-secret>,
C<minPinLength>, C<credBlob>), which are also checked for type.

=item allow_unsolicited_extensions

1 (the default) to ignore extension outputs you did not request, 0 to refuse
them. Only applies when C<requested_extensions> is given.

=back

The credential public key is checked before registration succeeds: its key
type must match its algorithm, it must parse, and an RSA key must be between
2048 and 4096 bits long, with an odd modulus and exponent.

This method croaks on errors. If the registration was successful, it returns a hashref with the following subkeys:

=over 4

=item credential_id

The base64url-encoded credential ID for this authenticator

=item credential_pubkey

The base64url-encoded public key for this authenticator, in COSE format

=item signature_count

The initial signature count of this authenticator

=item user_verified

1 if the authenticator verified the user (PIN, biometrics...) during this
operation, 0 otherwise

=item backup_eligible

1 if the credential may be backed up or synchronized between devices (a
multi-device credential), 0 if it is bound to a single device. This does not
change during the lifetime of a credential.

=item backup_state

1 if the credential is currently backed up, 0 otherwise

=item extension_results

The checked client extension outputs, without the unsolicited ones that were
ignored.

=item authenticator_extensions

The checked authenticator extension outputs, if the authenticator data had any.

=item discoverable

1 if the C<credProps> extension says the credential is discoverable (a
passkey that can sign in without a username), 0 if it says it is not. Absent
when C<credProps> was not returned.

=back

This information is supposed to be persisted in the Relying Party, usually in some sort of database

The following keys are also returned:

=over 4

=item attestation_result

Contains information about the result of the attestation validation

=over 4

=item type

The type of attestation used by the authenticator: C<None>, C<Self>,
C<Basic>, C<AttCA> or C<AnonCA>

=item trust_path

An arrayref of DER-encoded certificates provided by the authenticator

=item aaguid

The verified AAGUID of the authenticator, this is only provided if the
attestation was verified successfully and chained up to a trusted root
certificate.

=back

=back

=method validate_assertion

This method validates the registration response emitted by the authenticator.

It takes the following named arguments

=over 4

=item challenge_b64

The base64url-encoded challenge that was submitted to the authenticator

=item credential_pubkey_b64

The base64url-encoded credential public key corresponding to the received Credential ID

=item stored_sign_count

The current signature count in the Relying Party's database. Set it to 0 to
disable verification of the signature count

=item requested_uv

Whether or not the Relying Party required user verification for this operation.
Possible values are C<required>, C<preferred> (the default) and
C<discouraged>; any other value makes validation fail.

=item client_data_json_b64

The base64url-encoded client data received from the authenticator

=item authenticator_data_b64

The base64url-encoded authenticator data received from the authenticator

=item signature_b64

The base64url-encoded signature received from the authenticator

=item credential_id_b64

The base64url-encoded ID of the credential that signed (C<credential.id>).

=item allowed_credential_ids

An arrayref of the base64url-encoded credential IDs you offered in
C<allowCredentials>. Given and not empty, C<credential_id_b64> must be one of
them.

=item user_handle_b64

The base64url-encoded user handle the authenticator returned
(C<response.userHandle>), if any. Given, it must equal
C<expected_user_handle_b64>.

=item expected_user_handle_b64

The base64url-encoded user handle of the credential's owner, as given at
registration (C<user.id>).

=item require_user_handle

Set this when the user was not identified before the ceremony, as when a
passkey signs in without a username: the user handle is then required. You
find the credential, and so its owner and public key, from
C<credential_id_b64>, and the matching user handle proves the authenticator
holds that owner's credential.

=item extension_results, requested_extensions, allow_unsolicited_extensions

As for C<validate_registration>. An C<appid> output counts only if the
C<appid> extension was requested, when C<requested_extensions> is given.

=item appid

The AppID you passed in the C<appid> extension, if you did, for credentials
registered with the FIDO U2F API. When C<< extension_results->{appid} >> is
true, the authenticator data must carry the hash of this AppID instead of the
RP ID. Defaults to the C<appid> in C<requested_extensions>, then to the origin
that matched, as in earlier versions.

=back

This method croaks on errors. If the authentication was successful, it returns
a hashref with the following subkeys:

=over 4

=item signature_count

The new signature count, to be updated in the Relying Party's database

=item user_verified

1 if the authenticator verified the user (PIN, biometrics...) during this
operation, 0 otherwise

=item backup_eligible

1 if the credential may be backed up or synchronized between devices (a
multi-device credential), 0 if it is bound to a single device. This does not
change during the lifetime of a credential.

=item backup_state

1 if the credential is currently backed up, 0 otherwise

=item user_handle_b64

The user handle the authenticator returned, if any

=item extension_results

The checked client extension outputs, without the unsolicited ones that were
ignored.

=item authenticator_extensions

The checked authenticator extension outputs, if the authenticator data had any.

=back

=method convert_raw_ecc_to_cose

    my $cose_b64 = Authen::WebAuthn::convert_raw_ecc_to_cose($u2f_b64);

This method takes the base64url-encoded raw ECC key (U2F format) and converts
it to a base64url-encoded COSE representation. It can be useful for converting
existing U2F device registration to WebAuthen device registrations in your
Relying Party.


=head1 CAVEAT

This module supports the "none", "packed", "fido-u2f", "apple", "android-key"
and "tpm" attestation formats. Their certificates chain to the vendors' roots
(Apple's WebAuthn root, Google's hardware attestation roots, the TPM
manufacturers' roots), which you supply in C<trust_anchors>; this module does
not ship them or read the FIDO Metadata Service.

The supported public key algorithms are ES256, ES384, ES512, EdDSA (Ed25519),
RS256, PS256 and RS1, and RFC 9864's fully-specified ESP256, ESP384, ESP512 and
Ed25519, which in WebAuthn mean the same as ES256, ES384, ES512 and EdDSA.
Elliptic curve keys in compressed form are refused, as WebAuthn requires.

We plan to support additional attestation formats and algorithms in the future,
given enough time and/or sponsorship.
